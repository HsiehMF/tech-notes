# Tokenization & Context Window

Tokenization 將文字轉成模型可處理的 Token IDs；Context Window 限制模型單次可使用的上下文容量。兩者會影響 LLM 應用的資料量與用量。

[回到本章](README.md) · [AI Engineering 索引](../README.md)

## Tokenization：從文字到 Token

文字先經過 Tokenizer，被切分為 Token 並對應為 Token ID，再轉成向量供模型運算。

Token 不固定等於一個字或完整單字。切分方式取決於 Tokenizer；相同文字使用不同模型的 Tokenizer，Token 數可能不同。規劃上下文時應使用相應 Tokenizer 或 API 回傳的實際用量，不能直接把字數當成 Token 數。

## Context Window：單次的容量限制

Context Window 是單次模型處理上下文的容量上限。規劃請求時，需要考慮輸入與生成輸出所需的空間；模型與 API 可能另有最大輸出限制。

| 內容 | 用途 |
|---|---|
| 系統或應用指令 | 定義行為、任務規則及限制 |
| 使用者訊息 | 提供當下問題或任務 |
| 歷史對話 | 提供先前討論的脈絡 |
| 工具結果與外部資料 | 提供查詢結果、文件及操作證據 |
| 生成輸出 | 模型產生的回覆 |

歷史對話或檔案只有在應用程式將其載入當次上下文時，才會被模型使用。介面能看到整段對話，不代表每次呼叫都包含全部原文。

## Context Window 與 Token Usage 的差異

| 比較 | Context Window | Token Usage |
|---|---|---|
| 定義 | 單次可處理的容量上限 | 實際使用的 Token 數 |
| 計算範圍 | 單次呼叫 | 可記錄單次，也可跨多次累計 |
| 主要用途 | 判斷是否能容納資料 | 追蹤使用量與成本 |
| 是否可累積 | 容量本身不跨呼叫累積 | 使用量可以累積 |

例如：假設某模型的 Context Window 為 128K，應用程式執行了多次呼叫，每次使用量都在限制內，累計 Token Usage 仍可能超過 128K。這並不表示某一次呼叫超過容量。

## 上下文管理策略

| 策略 | 做法 | 優點 | 主要取捨 |
|---|---|---|---|
| Truncation | 移除部分內容以縮短上下文 | 簡單、額外運算成本低 | 被移除的資訊不再出現在當次輸入 |
| Sliding Window | 持續保留最近一段或固定預算內的訊息 | 適合連續對話 | 較早的關鍵資訊可能被排除 |
| Compaction | 將歷史內容濃縮為摘要 | 減少篇幅並保留部分脈絡 | 摘要可能遺漏細節或引入誤差 |

Sliding Window 常透過截斷較早內容實現，兩者不是互斥的方法。Compaction 也能與近期訊息保留、原始文件檢索搭配使用。

摘要應保留當前目標、已確認結論、重要限制與尚未完成事項。反覆摘要可能讓細節逐漸流失；需要精確資料時，應重新取得原始來源。

## 持久化資訊與模型記憶

把資訊存進檔案或資料庫，只是完成保存。模型要使用它，仍需由應用程式讀取、檢索並載入上下文。

例如持久化指令文件可保存持續適用的規則，但必須由工具依其載入機制提供給模型。涉及檔案限制時，還需搭配權限設定或變更檢查；指令文字本身不是權限機制。

## 實際應用

長時間分析文件或程式碼時，可採用以下做法：

1. 限制工具回傳量，只載入與問題相關的內容。
2. 將近期訊息與早期摘要組合成上下文。
3. 保存原始資料的位置，必要時重新讀取。
4. 讓持續適用的規則有可重複載入的來源。
5. 分別追蹤當次容量與累計用量。
